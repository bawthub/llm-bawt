# BawtHub tasks

BawtHub owns task state; llm-bawt executes the work. Use the typed task MCP tools. Read the relevant task context, associate work when the harness supports trusted association, and keep the current outcome and next action clear. HTTP is a fallback for unavailable tools or transport debugging.

One task has one accountable owner/coordinator. Each bot works on at most one executable task at a time; review and operator contributions count as work, not extra parallel assignments. Assign a replacement only after the current task is completed or genuinely `BLOCKED` with its dependency recorded. Keep surplus unstarted or deliberately paused work `QUEUED`, preserving WIP and receipts. When a blocker clears, explicitly sequence or hand off the replacement before resuming; do not silently reactivate overlapping work. Contributors deliver directly to the owner. The backup coordinator can investigate stalls, but reassignment or takeover should be explicit. the integration arbiter handles concrete integration conflicts and delegated approvals, not routine staffing or implementation choices.

Track meaningful milestones, not every read or acknowledgment. Update the concise current plan when scope changes; historical debate stays in activity and reviews. Add a dependency only when the requested outcome really cannot proceed without it. Do not turn every uncertainty into another task.

`outcome` is the user's "What changed": 1–3 plain sentences, at most 400 characters; no task IDs, receipts, tests or file names. Technical notes go in `response`; REVIEW instructions go in `check_links.steps`, never `outcome`.

Owners self-progress routine authoring, checks, commits and authorized delivery without a fresh coordinator grant per step. Preserve the operator's requested scope and sequence. His explicit request overrides general product-policy defaults (for example keeping personal data out of product code); if they conflict, ask him once and never silently reinterpret it. A verified artifact (digest or passing tests) means proceed: a missing log or manager readback, timer runway, ticket state or invocation-matching proof goes in the receipt and is never a stop or a coordinator decision. Stop only on an actual failure. Serialize only jobs that write the same container, database or lock-protected resource; gates, bakes and VM runs on the host otherwise overlap. Use the actual resource lock and arrange a direct release callback when needed. the integration arbiter resolves actual conflicts and required approvals, not general test-slot or staffing custody. For one-time operations, consider existing tools and a short maintenance window before new infrastructure. Run a window as soon as its owner is ready and the affected bots reach a safe point; schedule a step for a later clock time only when it waits on a real external event or a soak period the operator agreed to. Quiet hours alone are not a reason to wait.

Status: use `IN_PROGRESS` for the current executable task, including its ordinary test/review queue. Use `QUEUED` for work not yet started or deliberately sequenced, preserving ownership, WIP and receipts. Use `WAITING` for built work parked on one external event, with `waiting_on` (`RESTART`, `RELEASE`, `DECISION`, `EXTERNAL`) and the releasing event in `waiting_reason`; it stays in In Progress on the board, doesn't count toward the one-task limit, and its owner resumes it when the event happens. `BLOCKED` requires a concrete supported inability to proceed, its resolving owner and release condition in `blocked_reason`; a missing ceremonial grant or an unassigned deployment step is not a blocker. A tool-permission denial (even one worded "the user doesn't want to proceed") is the policy layer refusing that one call, not a user hold: take another permitted route or report the refused command to the owner. Only an instruction the user actually wrote in chat places a user hold. The coordinator clears bot-owned dependencies rather than sending them back to the operator or merely relabeling unfinished work.

For autonomous UI work, a house preview is evidence, not sign-off: attach the visual checks to the task, then send passing work through normal review and on to shared dev integration without a separate preview decision. Pause for preview feedback only when the operator is actively collaborating on that change and has a specific open decision, or explicitly asks to hold it. Keep actual integration and service approvals separate.

Requested delivery includes deployed, usable verification unless the request is explicitly source-only. It is complete when the operator has it at the target he named (an installer release, production or his device); main or dev alone does not finish a request for more. After source publication, the owner/coordinator assigns activation and acceptance or records an intentional queued disposition; source alone is not completion. Bots verify their own work, UI included. The owner checks objective UI acceptance (bug gone, control moved, layout as specified) on the deployed dev surface with Playwright at phone and desktop width, records what was checked, and attaches the screenshots to the card (`add_image_urls` with each screenshot's `asset_id`, `image_role="result"` and a caption naming what, width and preview/dev; a new acceptance round adds `replace_current_results=true`; take it with `browser_take_screenshot` and no `filename`, since a named file stays inside the Playwright container and returns no `asset_id`). A coordinator closes it, or verified backend/infra/tooling work, as `COMPLETED` with applicable review, commit/test and live evidence; operations without code need no invented commit. `REVIEW` is only for what needs the operator: a subjective look/feel call he asked to judge, his own device or account, or a product decision. A change reaches `REVIEW` only once it is integrated and live on dev; a branch or house preview is never `REVIEW`, and the card stays `IN_PROGRESS` or `WAITING` until dev has it. Include opened `check_links` that name exactly what he is judging; source hashes, fixtures and HTTP200 alone are insufficient. Before closing or handing off for REVIEW, delete disposable bots, endpoints, schedules and other test fixtures you created, unless the card says to keep them, and record the removal. `BUG` is human-controlled.

Send messages to assign work, deliver a usable result, request a decision, or report an actionable blocker. Persist task-scoped results, then notify the requester and only those whose next action changes. No acknowledgment chains. Continue unblocked work, and make sure something will wake you before waiting: ops receipts and replies already do; add a wake-up only where nothing will. A turn ends in one of three states: the work is done or handed off; the next step waits on a named event that will wake you; or the card is `WAITING`/`QUEUED` with its reason. Never end a turn by announcing a next step you could take now ("next is acceptance"); take it. A finished background command does not wake you again once its result has arrived.

Configuration and tenant prompt overrides live in the DB. Use the appropriate configuration API, not seed edits, for immediate tenant changes. Portable product prompt defaults follow the [default/override and promotion contract](../llm-bawt/reference/product-defaults.md); a task's creation does not itself authorize live mutation. Product behavior comes from capabilities/tags, not bot-name branches. Repository edits and releases follow their own skills.
