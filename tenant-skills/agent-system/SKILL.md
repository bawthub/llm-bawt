# BawtHub tasks

BawtHub owns task state; llm-bawt executes the work. Use the typed task MCP tools. Read the relevant task context, associate work when the harness supports trusted association, and keep the current outcome and next action clear. HTTP is a fallback for unavailable tools or transport debugging.

One task has one accountable owner/coordinator. Each bot works on at most one executable task at a time; review and operator contributions count as work, not extra parallel assignments. Assign a replacement only after the current task is completed or genuinely `BLOCKED` with its dependency recorded. Keep surplus unstarted or deliberately paused work `QUEUED`, preserving WIP and receipts. When a blocker clears, explicitly sequence or hand off the replacement before resuming; do not silently reactivate overlapping work. Contributors deliver directly to the owner. The backup coordinator can investigate stalls, but reassignment or takeover should be explicit. Gavel handles concrete integration conflicts and delegated approvals, not routine staffing or implementation choices.

Track meaningful milestones, not every read or acknowledgment. Update the concise current plan when scope changes; historical debate stays in activity and reviews. Add a dependency only when the requested outcome really cannot proceed without it. Do not turn every uncertainty into another task.

`outcome` is the user's "What changed": 1–3 plain sentences, at most 400 characters; no task IDs, receipts, tests or file names. Technical notes go in `response`; REVIEW instructions go in `check_links.steps`, never `outcome`.

Owners self-progress routine authoring, checks, commits and authorized delivery without a fresh coordinator grant per step. Preserve the user's requested scope and sequence. Serialize concrete shared writers or competing heavy jobs, not independent reads, source reviews or nonconflicting checks; use the actual resource lock and arrange a direct release callback when needed. Gavel resolves actual conflicts and required approvals, not general test-slot or staffing custody. For one-time operations, consider existing tools and a short maintenance window before new infrastructure.

Status: use `IN_PROGRESS` for the current executable task, including its ordinary test/review queue. Use `QUEUED` for work not yet started or deliberately sequenced, preserving ownership, WIP and receipts. Use `WAITING` for built work parked on one external event, with `waiting_on` (`RESTART`, `RELEASE`, `DECISION`, `EXTERNAL`) and the releasing event in `waiting_reason`; it stays in In Progress on the board, doesn't count toward the one-task limit, and its owner resumes it when the event happens. `BLOCKED` requires a concrete supported inability to proceed, its resolving owner and release condition in `blocked_reason`; a missing ceremonial grant or an unassigned deployment step is not a blocker. The coordinator clears bot-owned dependencies rather than sending them back to the user or merely relabeling unfinished work.

Requested delivery includes deployed, usable verification unless the request is explicitly source-only. After source publication, the owner/coordinator assigns activation and acceptance or records an intentional queued disposition; source alone is not completion. Bots verify their own work, UI included. The owner checks objective UI acceptance (bug gone, control moved, layout as specified) on the deployed dev surface with Playwright at phone and desktop width, records what was checked, and attaches the screenshots to the card (`add_image_urls` with each screenshot's `asset_id`; take it with `browser_take_screenshot` and no `filename`, since a named file stays inside the Playwright container and returns no `asset_id`). A coordinator closes it, or verified backend/infra/tooling work, as `COMPLETED` with applicable review, commit/test and live evidence; operations without code need no invented commit. `REVIEW` is only for what needs the user: a subjective look/feel call he asked to judge, his own device or account, or a product decision. Include opened `check_links` that name exactly what he is judging; source hashes, fixtures and HTTP200 alone are insufficient. Before closing or handing off for REVIEW, delete disposable bots, endpoints, schedules and other test fixtures you created, unless the card says to keep them, and record the removal. `BUG` is human-controlled.

Send messages to assign work, deliver a usable result, request a decision, or report an actionable blocker. Persist task-scoped results, then notify the requester and only those whose next action changes. No acknowledgment chains. Continue unblocked work, and make sure something will wake you before waiting: ops receipts and replies already do; add a wake-up only where nothing will.

Configuration and tenant prompt overrides live in the DB. Use the appropriate configuration API, not seed edits, for immediate tenant changes. Portable product prompt defaults follow the [default/override and promotion contract](../llm-bawt/reference/product-defaults.md); a task's creation does not itself authorize live mutation. Product behavior comes from capabilities/tags, not bot-name branches. Repository edits and releases follow their own skills.
