# Integration and publication

Authors send the integrator a ready revision, scope, review receipt and relevant checks. The integrator checks outstanding blockers, ownership, conflicts and secrets, then batches compatible work. Resolve genuine conflicts with the author; avoid new reviews for unchanged patches.

For llm-bawt/BawtHub, run one `make gate REV=<final-tip>` on the host for the reviewed batch and require its exact-SHA PASSED receipt. Reuse that receipt; do not full-gate each local iteration or pure rebase. A changed final tip needs its own gate. Attribute a failing check before choosing a repair or retry.

For llm-bawt/BawtHub, publish the gated SHA with `gate-push [-C <repo>] <SHA>`. It requires that receipt and pushes the branch and a `bawthub-gate PASSED <gate id>` note (`refs/notes/bawthub-gate`) atomically. CI skips the suites the gate already ran for a noted master/main SHA, and runs them for anything else. A plain `git push` is not a CI-only fallback: the repo pre-push hook accepts only an exact-SHA PASSED receipt and otherwise runs the full gate first (which needs Docker, so run it on the host). Any new SHA, including a rebase onto a version-only release commit, needs its own gate. Verify the remote and CI. Tenant images (app, agent-bridge, pocket-tts, voice-backend) no longer build per push; dispatch the repo's tenant publish workflow for an exact SHA when a deploy needs one. The integrator may finish publication instead of bouncing it back to the author. Coordinate the clean shared checkout's fast-forward with activation: it is mounted into running services, so incompatible source/schema changes need their planned rollout. After a verified push, fast-forward the shared checkout on the host with `git fetch -q origin && canonical-check --repo "$PWD" && git merge --ff-only origin/<canonical>` from that checkout (llm-bawt `master`, bawthub `main`). The check fails closed: on exit 1 do not fast-forward; stop and ping the owner with its JSON. It refuses a set `core.worktree` (git would report the new HEAD while the files land elsewhere), a toplevel that isn't the repo, and tracked dirt, so a dirty live tree is never moved over uncommitted work.

For a BawtHub publish changing `prisma/schema.prisma`, use the [back-to-back DB/source/frontend rollout](../../bawthub/references/pitfalls.md#prisma-schema-publication-can-leave-dev-apis-returning-503) when fast-forwarding the shared checkout; do not defer its restart or API probe until after the publication receipt.

For agent-skills, run relevant script checks and publish with `skills-sync <SHA>`; it verifies the pinned push before updating the live checkout. No application full-suite gate is needed for instruction-only changes.

A long-running check needs a durable callback/wakeup if the turn ends. Read the actual receipt before claiming success. A push alone does not prove service deployment. Use the repo's release guidance for activation and honor explicit user holds.

## Daily release strand check

Before choosing a daily release batch, refresh both origin tracking refs and run `stranded-check --dev-root <shared-root> --queue <current-queue.tsv> --baseline <acknowledged.tsv> --releases-since-baseline <N> --json` once. Save stdout, the queue snapshot, baseline revision and release-count evidence. Read `alarm_count` and `summary`, not all `findings`. Exit 0 means no strand alarms; exit 1 means a new or overdue strand; exit 2 means the scan could not run. Capture status under `set -e`. Route true strands to their owners with the integration arbiter copied; this is intake, not a global release veto.

The integration arbiter supplies the current queue: one tab-separated `TASK-N`, `bawthub` or `llm-bawt`, and full lowercase approved source SHA per row; use no heading (blank lines and `#` comments are fine). List any original reviewed SHAs the queued restack carries, not only its new tip. Only an exact task/repo/SHA match on a WAITING RELEASE card becomes `in-pipeline`: counted in JSON, not an alarm. REVIEW, COMPLETED and other WAITING cards still alarm if off branch. Without a queue file nothing is assumed queued; a malformed supplied file fails the scan.

Only the structured `targetRevision` field of APPROVE reviews on WAITING, REVIEW and COMPLETED cards updated within 30 days is read, never the review body. Set it to a commit SHA or repo-qualified SHAs such as `bawthub:<sha>; llm-bawt:<sha>`. Missing, non-Git, or unavailable targets are reported as `unverifiable-review`, one line per card including completed cards. `unverifiable_review_count` includes history. Use `new_unverifiable_card_count` and `unverifiable_reviews[].route_to` for new repairs, active cards first. `review_target_requests` retains the review IDs and reasons; route only records without `historical`. The baseline directive `# unverifiable-before: <UTC timestamp>` freezes the old review cohort at its creation time. Historical-only cards stay counted in JSON and show in plain output only with `--include-historical`; do not chase them. This is metadata repair, not a strand alarm, and does not change the exit status. A successfully resolved off-branch commit with inconclusive Git comparison remains an alarm.

Commit the baseline once after triage, not as a daily snapshot or an allowlist of everything old. Use `# release-anchor: <receipt-id>` and tab-separated `TASK-N`, repo, full reviewed SHA, disposition, landing SHA (or `-`), evidence. Dispositions: `integrated-edited`, `superseded`, `cancelled`, `parked`, `pending-integration`. Every quiet entry needs an explicit, evidence-backed disposition. Match exact card, repo and SHA; a newer SHA is not covered. Without a baseline the tool inventories all off-branch findings not already excluded or exactly queued. Keep installation-specific baselines outside product source.

For pending integration, record the full accepted landing SHA and map each reviewed variant it carries. The integration arbiter supplies the count of distinct **completed daily releases** after the anchor (anchor = 0; do not count retries, dry runs or each product batch separately). At 0 and 1, pending restacks appear once in `pending_integration`, not as alarms. At 2, a missing restack alarms even if still queued or its review aged out. A verified landing clears it. Do not reset the anchor or replace the pending pin merely to hide an overdue item.

Exact ancestry, `git cherry` equivalence and a complete reverse-only patch match against the pinned published tree can prove a patch present; partial matches are not enough. This does not prove a published change was never later reverted, every commit in a series landed, or an image includes it. Use exact card notes for separately triaged work: `Stranded-check: superseded|cancelled|parked <sha> — <reason>`. For verified artifact hashes use `Stranded-check: non-commit <token> — <evidence>`; this cannot hide a resolved product commit. Preserve the card response and do not mark work awaiting integration as superseded.

For an explicitly triaged, unavailable token on a COMPLETED card, add `Stranded-check: unresolvable-historical <token> — <reason>` to the card response, preserving the existing text. Use the exact token from the approval. Run once with `--include-historical` to retain the itemized disposition receipt, then leave the flag off daily runs. Daily output only counts this class; it does not list, route, or alarm on it. The flag only changes what is listed, not the exit status. A reopened card or a token that resolves to a product commit goes through normal checks again.

## Daily release skills refresh

Installed bots run the skills baked into the llm-bawt images from `tenant-skills/`. While preparing each daily llm-bawt batch, the integrator runs `export-product-skills tenant-skills` in an llm-bawt worktree from agent-skills `origin/main`. If the `BUNDLE.json` revision changes, commit the result into that batch so the normal gate and general-use scan cover it. A general-use failure goes back to the agent-skills author; ship the remaining batch without the refresh. Never refresh during the image build or commit directly to master.
