# Operations and maintenance

The [operations skill](../../bawthub-ops/SKILL.md) owns authorization, dispatch, receipts and the one-time maintenance path. Discover live slugs and schemas instead of relying on examples.

Typical operations: `llm-bawt.restart-app`, `llm-bawt.restart-bridge`, `llm-bawt.restart-aux`, `container.restart`, and the service-specific config-reconcile actions. A restart reloads source; it does not apply image, mount or environment changes. Reconcile actions keep the current image; do not substitute them for an upgrade.

Seed defaults are not live enablement: check `ops_list_operations(slug=..., include_disabled=true)` for a reconcile or `llm-bawt.cutover-plan` row rather than assuming it is disabled.

To move the GPU local-model bridge to another local image, use `llm-bawt.deploy-local-model-bridge-image` (full `sha256:` image ID; it probes `/embed` and restores the old container on failure) and `llm-bawt.rollback-local-model-bridge-image` (the deploy job ID). Seeding adds them without the install's `compose_config.interpolation_env` (e.g. `HOME`), so their first run refuses with `unset_compose_variable`. When enabling them, copy that object from the same service's live `reconcile-*-config` row with `PATCH /v1/ops/operations/{slug}`.

Agent harness upgrades (the daily `harness_version_check` card) ship as a rebuilt `claude-code-bridge` image. Bump the pins in `docker/agent-bridge-constraints.txt` and publish that commit, then build on the Docker host from the project directory of the canonical checkout at the published SHA: `docker compose build claude-code-bridge` (the shared `x-agent-bridge-image` build; it only tags, nothing restarts). Take the new full ID with `docker image inspect -f '{{.Id}}' <image>` and run `llm-bawt.deploy-claude-code-bridge-image` with that `image_id`; it import-checks the image, recreates the bridge (killing active agent sessions, resumed through quiesce), restores the old container on failure and records the previous image. To revert, run `llm-bawt.rollback-claude-code-bridge-image` with the deploy's `deploy_job_id`. When first enabled, both rows need the reconcile row's full `compose_config` (its `interpolation_env` and `compose_secrets`). Run them through `ops_run`: the op's quiesce drains bridge turns, including the caller's, and resumes them afterwards. Both run in process mode from the ops worker image, so a change to their code needs the rebuilt worker image described in the deploying reference.

Use a named service and `--no-deps` for an authorized manual recreation. A stopped service needs a verified start/recovery path. For data-loss risk, use the installation's backup runbook to verify fresh, recoverable backups.

Approval-gated jobs deliver durable completion receipts. If a quiesce result asks you to end the turn, end it without polling. Verify receipt state, exit code and target behavior. Inspect an uncertain existing job before retrying.

The approval pins the operation's `execution_mode`: `isolated` uses a separate worker container; `process` uses a bounded child of the ops reconciler. Existing Docker rows were backfilled to `isolated`; new rows default to `process`, not a fleet-wide migration. `bawthub.release-prod` uses the release executor's `process` value but orchestrates without starting a worker. A mode change requires fresh approval. See repo `ops/execution_mode.py` under `src/llm_bawt/` and `docs/OPERATIONS_RUNNER.md`.

For source-bound reconcile/cutover targets, `source_not_published` means the shared checkout is not the published branch tip; publish and align the checkout before requesting again. This is stricter than guarded restarts that accept a published ancestor. `snapshot_invalid` means the approved invocation's hash, bindings or execution mode no longer validate (or its persisted snapshot is missing); reconcile the reason and obtain fresh approval, never edit or replay the stale snapshot.

For ordered multi-service work, discover whether `llm-bawt.operation-sequence` is enabled. Its bounded `steps: [{operation, args}]` uses existing allowed catalog actions under one approval, one whole-window all-agent quiesce and one terminal callback. Children retain their individual admission checks and require bounded health verification. The parent receipt's structured `sequence.steps` carries every step's state, exit, health and rollback independently of text tails. It stops on failure; earlier successful restarts are not undone. A worker interruption preserves completed steps, reports an in-flight step as lost and skips the rest—never automatically resume or replay it.

The sequence seed is disabled until its capable worker and eligible live child rows are configured. Do not bypass that refusal or manufacture a multi-service smoke-test run; admission/tests precede the first genuine authorized use, which supplies live acceptance. Catalog grammar, supported kinds, fencing and activation are documented in `docs/OPERATIONS_RUNNER.md`.

Consult repo `docs/OPERATIONS_RUNNER.md` and `docs/OPS_CONFIG_RECONCILE.md` for implementation-specific activation or recovery. Use the installation’s private release runbook for local production activation. Historical incidents belong in task records, not new universal approval stages.
