# TASK-915 GPU handoff: measured baseline and safety contract

## Observed on Echo (2026-09-25, read-only)

- One NVIDIA GeForce RTX 5080: 16,303 MiB total, 3,819 MiB free, 12,021 MiB used (`nvidia-smi` on the host). GPU processes: two `moshi-server` processes reporting 8,204 and 2,758 MiB. Both `bawthub-stt-1` and `bawthub-tts-1` were healthy. These readings are a snapshot, **not** a calibrated Wan peak or a durable VRAM reservation.
- The `llm-bawt-local-model-bridge` is healthy at the container level and reports Wan installed (34,201,418,400 bytes on disk), worker ready, and no active video job. Its `nvidia-smi` returns `Failed to initialize NVML: Unknown Error`; `torch.cuda.is_available()` is false and `torch.cuda.mem_get_info()` raises `No CUDA GPUs are available`. Container health and disk installation therefore cannot be used as evidence of GPU readiness.
- `local_model_bridge.video_server.VideoJobs` permits one active subprocess, rejects another request with 409, and keeps jobs only in memory. `video_worker.run_job()` loads Wan from the managed HF hub cache with `local_files_only=True`, enables sequential CPU offload, then exits after **every** render. The currently installed weights are distinct from GPU residency. `video_models.remove()` deletes installed weights and must never be called for a VRAM handoff.
- The local model inference process has a separate `LocalModelInference` cache and `unload()` method in `local_model_bridge/inference.py`; there is no coordinated status/unload control shared with video or Moshi. BawtHub voice uses `/v1/realtime` and a 4-slot process semaphore; it exposes no authoritative active-call counter or admission barrier for preventing a new call between a safety check and a stop.
- The enabled ops catalog offers restarts only (`llm-bawt.restart-app`, `llm-bawt.restart-aux`, `bawthub.restart-frontend`, `llm-bawt.restart-bridge`, `container.restart`). **There is no supported, enabled Moshi STT/TTS stop/start operation.** The separate Docker UI's `/api/docker/containers/:id/:action` is a manual interface, not an ops-authorized transition executor. Neither route may be repurposed from a video worker. The underlying ops executor supports `start`/`stop`, but operator-reviewed, allowlisted actions would have to be created/enabled and permissioned separately.

## Transition contract to implement when prerequisites are available

1. **Single owner and admission authority.** Durable states: `unknown`, `voice`, `video`, `transitioning`, `recovery_required`; durable transition record includes source/target, exact actions, consent identity and one-use nonce, expiry, current phase, service job IDs, and last verified observations. An atomic database claim/lease plus fencing token serializes render admission, voice admission, and transition execution across processes. A process restart with an in-progress phase moves to `recovery_required`, not automatic replay of destructive actions.
2. **Fresh preflight on every acquisition/confirmation.** Collect timestamped host free/total VRAM and per-process allocations, container and local-model health/residency, disk installation separately, pending video work, and authoritative active voice-call count. Require all observations to be fresh at execution time; telemetry or admission failure blocks switching. Estimate **peak** Wan demand by resolution/duration and Moshi peak by service from measured runs; add an explicit headroom margin (proposed floor: 2 GiB, subject to profiling). No validated Wan peak exists in the repository, so the current data cannot substantiate any successful-capacity decision. Never infer free capacity merely by summing process allocations or trusting container `healthy`.
3. **Specific consent, not generic control.** If insufficient capacity, offer the affected services, exact ordered unload/stop/start actions, estimated change in VRAM with uncertainty, and expected voice/video disruption. Bind confirmation to that immutable transition, its preflight snapshot/version and expiry; recheck before execution. Denial/expiry mutates nothing. A video grant cannot authorize a later voice handoff or another infrastructure action. The ops policy and operator enablement remain independent gates after Nick's UI consent.
4. **Transitions and stable modes.** Video: lock admission, reject active calls, drain queued work, unload competing local models only via a safe bridge interface, stop idle Moshi STT/TTS via *dedicated enabled ops actions*, verify terminal ops jobs and service state, recheck VRAM, load Wan offline, verify residency, set owner `video`, then process serialized jobs without per-job load/unload. Voice: stop admitting new video, finish current job, park/unload Wan (without touching disk cache), verify VRAM, start both Moshi services through their dedicated ops actions, verify health, set owner `voice`. Stay in the chosen mode until another explicitly consented transition. No automatic restoration and no default idle policy.
5. **Failure/recovery.** Persist phase before and after each external action. Unknown ops outcome, stale telemetry, failed stop/start/health or interrupted process leaves a truthful `recovery_required` state with the last known action/job and a manual reconcile path. Never blindly retry an uncertain stop/start, interrupt an active call, or offer a button that bypasses ops approval. On restart reconcile read-only observations and present a new recommendation/consent if necessary. No network model downloads or cache deletion in any resource transition.

## Prerequisites before executable handoff or acceptance testing

- Fix GPU device visibility in `llm-bawt-local-model-bridge` and obtain fresh, authoritative host GPU telemetry through a narrowly scoped supported interface (not a guessed in-container `nvidia-smi`). This involves operational changes outside this task's permission to mutate services.
- Define operator-owned dedicated Moshi STT/TTS start and stop ops actions and approval rules. Seeded-but-disabled operations alone do not make a transition runnable; Nick/operator must review and enable them. The generic Docker UI route is not a substitute.
- Instrument cross-process active voice sessions and an atomic admission barrier that coordinates websocket accepts with transitions, plus a reliable safe local-model unload/status path. Profile Wan and Moshi peak demand on the actual GPU to choose enforceable thresholds. Until this evidence exists, every preflight must fail closed rather than promise a capacity-safe switch.

## Implementation progress (2026-09-26)

- The local-model bridge was restarted through the approved `llm-bawt.restart-aux` operation; CUDA now initializes there. This does **not** release Moshi's ~12 GiB or prove Wan fits. The bridge now has an on-demand single-GPU telemetry endpoint (`/gpu/telemetry`); the app's `/v1/media/local-video/gpu` returns telemetry, model installation/residency and durable render-claim counts alongside ownership status. Telemetry errors report `ready: false`, never a guessed VRAM allowance. Its read-only preflight reports stale/malformed telemetry, active voice/video work, unavailable voice admission, disabled Moshi ops, and the unmeasured Wan peak. It always returns `switch_ready: false`. The ops agent summary now includes the actual `enabled` flag rather than treating every operation as disabled. Source changes have not been activated in the running app/bridge.
- The voice admission barrier exists in BawtHub; its park/unpark routes are now async to run on the same event loop as websocket admission. Active or unidentified sockets veto a park. Direct Moshi TTS and STT startup, including service discovery probes, now claim GPU work before connecting and release on error/shutdown; the active-work count also vetoes a park. Compose has a default URL to the BawtHub `/api` proxy and optional shared-token plumbing, but the internal operator token is **not configured** on the current voice backend or llm-bawt app. Neither service can yet perform an authenticated handoff.
- `GpuHandoffStore` persists owner, generation, scoped one-use expiring offers, ordered action cursor, pending action, and last operation job. A confirm consumes the token atomically; ambiguous action states and interrupted transitions must go to `recovery_required` and cannot be silently replayed. Both the app and private video server now gate video submission through this ledger; the server also durably claims queued renders. App startup marks interrupted transitions and video-server startup marks orphaned claims or lost video residency for recovery. It is not yet wired into voice ownership acquisition, transition execution, or a verified manual recovery path. A stored owner of `unknown` is not proof that the current services are stopped or safe.
- Four exact Moshi start/stop operation seeds exist, **disabled** by default. No operation has been seeded/enabled in the live catalog, and no Moshi service was stopped or started. Studio now has a read-only owner/VRAM/installed-vs-resident/claims/preflight/recovery readout but no misleading switch button.
- `WanPipelineRunner` can reuse one offline-loaded pipeline for consecutive same-mode renders, reload when switching text/image modes, and explicitly drop its references. A private JSON-lines worker command loop handles serialized render/status/unload commands; tests cover reuse, unload, and failure. After a failed command the loop exits, rather than trusting an uncertain CUDA state for the next render. A standalone `ResidentVideoWorker` supervisor now serializes child commands, checks output and process status, and fails closed on missing replies or uncertain spawn/unload; fake-process tests pass. The private video server now admits up to eight pending requests against durable render claims and serializes them through one resident subprocess. Tests verify back-to-back queue execution and one child, bounded queue rejection, failure blocking all queued claims, and unexpected worker exits. The owner defaults to `unknown`, so none of this can run without a verified, consented handoff. **The reciprocal unload/coordinator and live capacity proof are still missing**; unit tests do not demonstrate Wan fitting the RTX 5080 or authorize switching.
- **Still required before switching:** configure a shared operator credential via an authorized compose recreation; operator review and enable the four exact ops; build a coordinator that performs fresh preflight, trusted user-scoped consent, action dispatch via the ops approval path, terminal job/health verification and reconciliation; complete reciprocal voice admission and release the resident Wan worker on consented voice handoff; wire Studio/voice consent and recovery UI; test concurrent calls, denied consent, crashes, and actual peak VRAM at 480p. Do not run Wan under the current ~3.8 GiB free as an informal capacity test.

The original observations above describe the initial read-only baseline; this section records subsequent changes without implying the handoff is live.
